# 系统化调试

## 概览

**核心原则：** 动手修之前，永远先找到 root cause（根本原因）。只治表面的症状，就是失败。

**违背这套流程的字面要求，就是违背调试的精神。**

## 铁律

```
不先做 ROOT CAUSE 调查，就不许动手修
```

Phase 1 没走完，就不能提修复方案。

## 什么时候用

任何技术问题都适用：
- Test 失败
- 线上环境的 bug
- 行为异常
- 性能问题
- 构建失败
- 集成问题

**下面这些情况尤其要用：**
- 时间紧张（紧急关头，人特别容易靠猜）
- 「就快速改一下」看起来理所当然
- 你已经试过好几个修法
- 上一次的修复没管用
- 你还没完全搞懂问题

**下面这些情况不要跳过：**
- 问题看起来很简单（简单 bug 也有 root cause）
- 你在赶时间（着急必然返工）
- 领导要求立刻修好（系统化调试比瞎折腾更快）

## 四个阶段

每个阶段都必须走完，才能进入下一个。

### Phase 1：Root Cause 调查

**动手修之前，先做这些：**

1. **仔细读报错信息**
   - 别跳过 error 或 warning
   - 它们常常就带着确切的解法
   - 完整读完 stack trace（报错时打印的调用堆栈，从下往上看能追到出错源头）
   - 记下行号、文件路径、error code

2. **稳定地复现**
   - 能可靠地触发它吗？
   - 确切的步骤是什么？
   - 每次都发生吗？
   - 如果复现不了 → 去收集更多数据，别猜

3. **检查最近的改动**
   - 改了什么可能导致这个问题？
   - Git diff、最近的 commit
   - 新增的依赖、配置改动
   - 环境差异

4. **在多组件系统里收集证据**

   **当系统有多个组件时（CI → build → signing，API → service → database）：**

   **提修复方案之前，先加诊断埋点：**
   ```
   对每一个组件边界：
     - 记录什么数据进入组件
     - 记录什么数据离开组件
     - 验证环境/配置有没有正确传递
     - 检查每一层的状态

   先跑一次，收集证据，看问题出在哪一层
   然后分析证据，定位出故障的组件
   再深入调查那个具体的组件
   ```

   **例子（多层系统）：**
   ```bash
   # Layer 1: Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # Layer 2: Build script
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # Layer 3: Signing script
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # Layer 4: Actual signing
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这样能看出：** 哪一层失败了（secrets → workflow ✓，workflow → build ✗）

5. **追踪数据流**

   **当 error 出现在调用栈很深的地方时：**

   完整的反向追踪技巧见本目录下的 `root-cause-tracing.md`。

   **简版：**
   - 那个坏值是从哪里来的？
   - 谁用这个坏值调用了这里？
   - 一直往上追，直到找到源头
   - 在源头修，不要在症状处修

### Phase 2：模式分析

**先找出模式，再动手修：**

1. **找出能正常工作的例子**
   - 在同一个 codebase 里找类似的、能跑通的代码
   - 有什么能跑通的东西和出问题的那块很像？

2. **和参照实现对照**
   - 如果要照着某个模式实现，就把参照实现完整读一遍
   - 别只看个大概——每一行都读
   - 完全理解这个模式之后再套用

3. **找出差异**
   - 能跑通的和出问题的，差在哪？
   - 把所有差异都列出来，再小也列
   - 别想当然地认为「这点差异不可能有影响」

4. **搞懂依赖关系**
   - 它还需要哪些别的组件？
   - 用到什么设置、配置、环境？
   - 它做了哪些假设？

### Phase 3：假设与验证

**用科学方法：**

1. **只提一个假设**
   - 明确说出来：「我认为 X 是 root cause，因为 Y」
   - 把它写下来
   - 要具体，别含糊

2. **做最小验证**
   - 用尽量小的改动去验证假设
   - 一次只动一个变量
   - 别同时修好几处

3. **验证之后再往下走**
   - 管用了吗？管用 → 进 Phase 4
   - 没管用？提一个全新的假设
   - 不要在原来的基础上再叠更多修复

4. **当你不知道的时候**
   - 就说「这块我不懂」
   - 别装懂
   - 去求助
   - 再多查查

### Phase 4：实施

**修 root cause，不修症状：**

1. **先写一个会失败的 test case**
   - 用最简单的复现方式
   - 能自动化就自动化
   - 没有测试框架就写个一次性测试脚本
   - 动手修之前必须先有这个
   - 写规范的失败 test，用 `superpowers:test-driven-development` 技能

2. **只实施一个修复**
   - 针对已定位的 root cause
   - 一次只改一处
   - 别顺手「既然来了就一起改」
   - 别把重构捆在一起

3. **验证修复**
   - 现在 test 过了吗？
   - 有没有弄坏别的 test？
   - 问题真的解决了吗？
   - 宣布成功之前，用 `superpowers:verification-before-completion` 技能

4. **如果修复不管用**
   - 停下
   - 数一数：你已经试了几个修复？
   - 如果少于 3 个：回到 Phase 1，带着新信息重新分析
   - **如果达到或超过 3 个：停下，质疑架构（见下面第 5 点）**
   - 没经过架构层面的讨论，不要贸然尝试第 4 个修复

5. **如果 3 个以上修复都失败了：质疑架构**

   **说明架构有问题的信号：**
   - 每修一处，就在别的地方暴露出新的共享状态、耦合或问题
   - 修复要落地，得做「大规模重构」
   - 每修一处，都在别处制造出新症状

   **停下，质疑根本假设：**
   - 这个模式从根上说得通吗？
   - 我们是不是「纯粹靠惯性硬撑着」？
   - 该重构架构，还是继续修症状？

   **尝试更多修复之前，先和你的人类搭档讨论**

   这不是假设错了——这是架构错了。

## 危险信号 —— 停下，照流程走

如果你发现自己心里冒出这些念头：
- 「先快速修一下应付过去，回头再查」
- 「就把 X 改改看行不行」
- 「一次改好几处，跑一下 test」
- 「test 先跳过，我手动验一下」
- 「大概是 X 的问题，我来修它」
- 「我没完全搞懂，但这样也许能行」
- 「模式上说是 X，但我换个方式改改看」
- 「主要问题有这几个：[没做调查就列出一堆修复]」
- 还没追踪数据流就提出方案
- **「再试最后一次修复」（已经试了 2 个以上时）**
- **每修一处，都在别的地方冒出新的问题**

**以上任何一条出现，都意味着：停下，回到 Phase 1。**

**如果 3 个以上修复都失败了：** 质疑架构（见 Phase 4.5）

## 人类搭档给的信号：你走错了

**留意这些纠正：**
- 「这事到底发生了吗？」—— 你没验证就做了假设
- 「它能让我们看到……吗？」—— 你本该加证据收集的
- 「别猜了」—— 你在没搞懂的情况下就提修复
- 「再往深里想想」—— 要质疑根本假设，不只是症状
- 「我们卡住了？」（不耐烦的语气）—— 你的方法不管用

**看到这些信号：** 停下，回到 Phase 1。

## 常见的自我开脱

| 借口 | 现实 |
|--------|---------|
| 「问题很简单，不用走流程」 | 简单问题也有 root cause。对简单 bug 来说，流程很快。 |
| 「紧急情况，没时间走流程」 | 系统化调试比猜来猜去瞎折腾更快。 |
| 「先试一下这个，然后再调查」 | 第一个修复定下了调子。从一开始就做对。 |
| 「等确认修复管用了，再补 test」 | 没 test 的修复站不住脚。先写 test 才能证明。 |
| 「一次改好几处省时间」 | 没法判断到底哪处起了作用，还引入新 bug。 |
| 「参照实现太长，我照着模式改改就行」 | 一知半解必然出 bug。要完整读完。 |
| 「我看到问题了，我来修」 | 看到症状 ≠ 理解 root cause。 |
| 「再试最后一次修复」（已经失败 2 次以上） | 失败 3 次以上 = 架构问题。质疑模式，别再修了。 |

## 速查表

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. Root Cause** | 读报错、复现、检查改动、收集证据 | 搞懂是什么（WHAT）和为什么（WHY） |
| **2. Pattern** | 找可用的例子、做对照 | 找出差异 |
| **3. Hypothesis** | 提假设、最小化验证 | 假设被证实，或提出新假设 |
| **4. Implementation** | 写 test、修复、验证 | Bug 解决，test 全过 |

## 当流程告诉你「没有 root cause」时

如果系统化调查发现，问题确实是环境导致、跟时序有关，或是外部原因：

1. 流程你走完了
2. 把你调查了什么记录下来
3. 实施合适的应对（重试、超时、报错提示）
4. 加上监控/log，方便日后排查

**但是：** 95% 说「没有 root cause」的情况，都是调查没做透。
