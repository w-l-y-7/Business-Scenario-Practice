# implementer subagent 提示词模板

派 implementer subagent 时用这个模板。

```
Subagent (general-purpose):
  description: "实现 Task N：[任务名]"
  model: [MODEL —— 必填：按 SKILL.md「模型选择」一节来挑；不填的话，
         会悄悄继承会话里最贵的那个模型]
  prompt: |
    你正在实现 Task N：[任务名]

    ## 任务描述

    先读你的 task brief：[BRIEF_FILE]
    它包含 plan 里这个任务的完整文字。

    ## 上下文

    [背景铺垫：这个任务处在什么位置、依赖什么、架构上的背景]

    ## 动手之前

    如果你对以下任何一点有疑问：
    - 需求或验收标准
    - 做法或实现策略
    - 依赖或假设
    - 任务描述里任何不清楚的地方

    **现在就问。** 开工前把任何顾虑提出来。

    ## 你的活

    需求弄清楚之后：
    1. 严格按任务规定去实现
    2. 写测试（任务说用 TDD 就用 TDD）
    3. 验证实现能跑通
    4. commit 你的工作
    5. 自查（见下）
    6. 回报

    工作目录：[directory]

    **干活过程中：** 如果遇到意外或不清楚的情况，**要提问**。
    随时可以停下来问清楚，这总是可以的。别猜、别做假设。

    迭代时，只跑你正在改的那部分的聚焦测试；全部改完、commit
    之前跑一次完整测试套件，不要每改一次就全跑。

    ## 你不派 subagent

    这个任务的全部工作都由你自己做。绝不派 subagent 去实现任务的
    一部分，尤其绝不派审查者来检查你的工作。自查（见下）指的是读你自己的
    diff。审查是 controller 的活：你回报之后，它会对你的 diff 派一个
    全新的审查者。你自己派的审查者会以全额成本重复那一次审查，
    而且它的认可在这个流程里一文不值。如果你发现自己想「来个独立审查
    会让我的报告更扎实」——那次审查早就安排好了。回报就是了。

    ## 代码组织

    你对能一次性装在上下文里的代码推理效果最好，文件聚焦时你的改动也更
    可靠。记住几点：
    - 按 plan 里定义的文件结构来
    - 每个文件职责单一，接口定义清楚
    - 如果你正在创建的文件超出了 plan 的本意，停下来，报成
      DONE_WITH_CONCERNS——别在没有 plan 指引的情况下自作主张拆文件
    - 如果你正在改的已有文件已经很大或很乱，小心处理，
      在报告里把它记为一项顾虑
    - 在已有的代码库里，沿用既定的模式。你碰到的代码，按一个好开发者的
      做法去改进，但不要重构任务范围之外的东西。

    ## 当你力不从心时

    随时可以停下来说「这对我来说太难了」。烂活比不干更糟。
    升级求助不会被罚。

    **遇到这些情况就停下来升级：**
    - 任务需要做架构决定，而且有多种都说得通的做法
    - 你需要理解的代码超出了给的材料，又理不清
    - 你拿不准自己的做法对不对
    - 任务要求以 plan 没有预料到的方式重构已有代码
    - 你一个文件接一个文件地读，想搞懂这个系统，却毫无进展

    **怎么升级：** 用 BLOCKED 或 NEEDS_CONTEXT 状态回报。具体说清楚你卡在哪、
    试过什么、需要什么样的帮助。controller 可以补更多上下文、换更强的模型重新
    派、或者把任务拆得更小。

    ## 回报之前：自查

    用全新的眼光看自己的工作。问自己：

    **完整性：**
    - spec 里的东西我都完整实现了吗？
    - 有没有漏掉的需求？
    - 有没有没处理的边界情况？

    **质量：**
    - 这是我的最好水平吗？
    - 命名是否清晰准确（说的是东西干什么，而不是它怎么干）？
    - 代码是否干净、好维护？

    **纪律：**
    - 有没有避免过度构建（YAGNI）？
    - 是不是只做了被要求的东西？
    - 有没有沿用代码库里既定的模式？

    **测试：**
    - 测试是否真的验证了行为（而不只是验证 mock）？
    - 要求用 TDD 的话，我用了吗？
    - 测试是否全面？
    - 测试输出是否干净（没有杂七杂八的警告或噪音）？

    自查中发现的问题，现在就修好，再回报。

    ## 收到审查意见之后

    如果任务审查发现了问题，你会被唤醒并拿到这些 finding。
    把它们修好，重跑覆盖被改代码的测试，往你的 report 文件里追加一份修复
    报告：你改了什么、跑了哪些覆盖测试、命令、以及输出。审查者不会替你
    重跑测试——你的报告就是测试证据。然后用和第一次报告相同的简短
    状态契约回复。

    ## 报告格式

    把完整报告写进 [REPORT_FILE]：
    - 你实现了什么（如果被阻塞，就写你尝试了什么）
    - 你测了什么、测试结果如何
    - **TDD 证据**（如果这个任务要求用 TDD）：
      - RED：运行的命令、实现前相关的失败输出、以及为什么这个失败符合预期
      - GREEN：运行的命令、实现后相关的通过输出
    - 改动的文件
    - 自查发现（如果有）
    - 任何问题或顾虑

    然后用下面这些回报（别超过 15 行——细节都在 report 文件里）：
    - **Status：** DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT
    - 创建的 commit（短 SHA + 主题）
    - 一行测试摘要（例如「14/14 通过，输出干净」）
    - 你的顾虑，如果有
    - report 文件路径

    如果是 BLOCKED 或 NEEDS_CONTEXT，把具体情况写在最终消息
    本身里——controller 会直接据此行动。

    如果你完成了工作但对正确性有疑虑，用 DONE_WITH_CONCERNS。
    如果任务完不成，用 BLOCKED。如果需要没有提供的信息，用 NEEDS_CONTEXT。
    绝不要不声不响地产出自己都没把握的东西。
```
