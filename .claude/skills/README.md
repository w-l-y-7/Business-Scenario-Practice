## 先搞清楚一件事

这些文件是**写给 Claude 读的操作指令**，不是给你背的。你不需要记住它们。

- **正常用法**：用自己的话把需求说清楚就行，Claude 会自己去挑用哪个技能。比如「帮我算一下这个基金组合的夏普比率」，它自己就会去找相关的技能。
- **想点名**：也可以直接打 `/技能名`，例如 `/brainstorming`、`/systematic-debugging`。

它们原本是为**软件工程师写代码**设计的。你做金融科技课题，用得上的是里面那套「想清楚 → 拆计划 → 验算 → 出错找根因」的方法，用不上的是跟代码版本管理有关的那几个。

## 第一梯队：你大概率真用得上

| 技能 | 干什么 | 对你意味着什么 |
| --- | --- | --- |
| **brainstorming** | 动手前先把你到底要什么问清楚，提出 2-3 个方案让你选 | 写论文、做数据分析、搭一个小工具之前用它。**能省下大量返工** —— 很多人卡住不是不会做，是一开始就没想清楚要做啥 |
| **writing-plans** | 把复杂任务拆成一份分步计划文档 | 课题一复杂就容易乱。用它先把「第一步做什么、第二步做什么」列出来 |
| **systematic-debugging** | 遇到报错或结果不对，先系统性地找根因，别瞎改 | 程序跑不出结果、数字对不上时用它。核心是「先定位原因，再动手改」 |
| **test-driven-development** | 先写检查程序，再写实现 | 金融计算的关键技能。算收益率、估值、手续费这些东西，**先写下「我期望结果是多少」，再让它去算**，能挡住绝大多数算错 |
| **verification-before-completion** | 声称「做完了」之前，必须真的跑一遍验证 | 防止被忽悠。不管是 Claude 说完成了，还是你自己觉得做完了，都先验一遍再下结论 |

## 第二梯队：偶尔用得上

| 技能 | 干什么 | 什么时候找它 |
| --- | --- | --- |
| **writing-skills** | 教你怎么写一个新技能、改成自己的 | 你在搭 workspace 自动化，想把自己常做的金融分析流程固化成技能时用它 |
| **receiving-code-review** | 收到审查意见后怎么严谨处理，不盲从 | 让人（或别的 AI）检查你东西之后，用它来判断哪些意见该听 |
| **requesting-code-review** | 主动请求审查 | 一份分析做完了，想找个人挑毛病 |
| **dispatching-parallel-agents** | 有 2 个以上互不相干的事，同时开工 | 比如同时处理 5 个公司的财报，互相不依赖 |
| **visual-companion**（属 brainstorming） | brainstorming 的可视化辅助 | 需要画图讨论设计时 |

## 第三梯队：暂时不用管

这几个是纯软件开发流程用的，跟金融课题关系不大。知道有就行，不用学。

| 技能 | 干什么 | 为什么你用不上 |
| --- | --- | --- |
| **using-superpowers** | 这套技能的入口说明 | 每次会话自动加载，你不用管 |
| **using-git-worktrees** | 给代码开一个互不干扰的独立工作副本 | 多人协作改同一个代码库时才需要 |
| **finishing-a-development-branch** | 一个开发分支做完了怎么合并、清理 | 同上 |
| **executing-plans** | 在单独会话里按计划逐步执行 | 大工程才需要 |
| **subagent-driven-development** | 用子代理执行计划里的独立任务 | 同上 |

## 你可能会有的疑问

**这些技能会自己跳出来打断我吗？**
不会。技能只在相关时才被调用。不过 `using-superpowers` 会要求 Claude 在每个任务开始前先想一下「有没有合适的技能」，所以你会感觉它偶尔会先来问你几个问题 —— 那通常是好事。

**「子代理」「worktree」「分支」这些词还是看不懂怎么办？**
直接问 Claude。你可以说「用大白话解释一下 subagent 是什么」，它会用金融场景给你类比。

**翻译过了，以后还想跟上原作者更新怎么办？**
翻译后这些文件就和英文原版分叉了，直接覆盖会丢中文。原始英文版备份在 `C:\Users\王\AppData\Local\Temp\superpowers-clone`（临时目录，可能被系统清理，要长期保留得另存一份）。
